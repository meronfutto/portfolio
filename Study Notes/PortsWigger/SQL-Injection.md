SQL-инъекция – это уязвимость, при которой пользовательский ввод меняет смысл SQL-запроса, отправляемого приложением в базу данных.

SELECT name, price FROM products
WHERE category = 'Книги'' AND released = 1;
Здесь есть нюанс: в SQL две одинарные кавычки подряд внутри строки обычно обозначают одну кавычку как символ данных. Поэтому в таком запросе строка остаётся не закрытой и обычно возникает синтаксическая ошибка.

SQL-комментарий ('--'). База данных игнорирует всё после него до конца строки. В некоторых СУБД после -- нужен пробел.

Например:
SELECT name, price FROM products
WHERE category = 'Книги'-- ' AND released = 1;
Часть после -- становится комментарием, поэтому условие AND released = 1; больше не участвует в отборе. Это уже SQL-инъекция: пользовательский ввод изменил логику запроса – убрал проверку публикации товара.

# AND и OR в SQL

## Как работает WHERE

WHERE проверяет условие отдельно для каждой строки таблицы.
Если условие истинно, строка попадает в результат.

## AND — оба условия должны быть истинными

| A | B | A AND B |
|---|---|---|
| Истина | Истина | Истина |
| Истина | Ложь | Ложь |
| Ложь | Истина | Ложь |
| Ложь | Ложь | Ложь |

Пример:

    WHERE category = 'Книги' AND released = 1

Выбираются только товары, которые одновременно:
- относятся к категории «Книги»;
- опубликованы.

## OR — хотя бы одно условие должно быть истинным

| A | B | A OR B |
|---|---|---|
| Истина | Истина | Истина |
| Истина | Ложь | Истина |
| Ложь | Истина | Истина |
| Ложь | Ложь | Ложь |

Пример:

    WHERE author = 'Анна' OR is_public = 1

Выбираются все статьи Анны и все публичные статьи
любых авторов.

OR не означает «если ничего не нашлось по первому
условию, использовать второе». Проверка происходит
отдельно для каждой строки.

## Условие, которое всегда истинно

1 = 1 всегда истинно.

    WHERE author = 'Анна' OR 1 = 1

Выбираются все строки: второе условие истинно
для каждой строки независимо от автора.

    WHERE author = 'Анна' AND 1 = 1

Выбираются только статьи Анны: второе условие
не создаёт дополнительного ограничения.

Правила:
- A OR TRUE → TRUE
- A AND TRUE → A

## Изменение фильтра через SQL-инъекцию

Приложение собирает SQL-запрос склеиванием строк,
вставляя пользовательский ввод прямо в текст запроса.

Исходный запрос:

    SELECT name, price FROM products
    WHERE category = 'Книги' AND released = 1;

Он возвращает название и цену только опубликованных книг.

### Пользовательский ввод

    Книги' OR 1=1-- 

После двух дефисов здесь стоит пробел.

### Получившийся запрос

    SELECT name, price FROM products
    WHERE category = 'Книги' OR 1=1-- ' AND released = 1;

### Как работает инъекция

1. Кавычка после слова «Книги» закрывает строковое значение.
2. OR 1=1 делает условие WHERE истинным для каждой строки.
3. Два дефиса начинают комментарий до конца строки.
   Проверка AND released = 1 больше не действует.

Пробел после двух дефисов нужен для совместимости
с некоторыми СУБД, например MySQL.

По смыслу база выполняет:

    SELECT name, price FROM products
    WHERE category = 'Книги' OR 1=1;

### Результат

Возвращаются все товары, включая неопубликованные
и относящиеся к другим категориям.

Для каждого товара возвращаются только столбцы
name и price, указанные в SELECT.

### Причина уязвимости

Пользовательские данные стали частью SQL-кода
и изменили логику запроса.

## Последствия SQL-инъекции

- Чтение данных, недоступных обычному пользователю.
- Возможная утечка хешей паролей, платёжных
  и персональных данных.
- При достаточных возможностях и правах —
  изменение или удаление данных.
- В отдельных случаях — закрепление в системе.
- Для организации — потеря доверия и возможные штрафы.

Масштаб последствий зависит от запроса, СУБД
и прав приложения в базе данных.

SQL-инъекция не означает автоматический доступ
ко всей базе или захват сервера.

## Как проверять наличие SQL-инъекции

Основной принцип: изменять ввод и сравнивать ответы
приложения с обычным ответом.

Нужно искать повторяемые изменения, которые соответствуют
предполагаемой работе SQL-запроса.

### Точки входа

Проверяем места, через которые приложение получает данные:
- параметры URL;
- поля форм и данные в теле запроса;
- cookies;
- HTTP-заголовки.

Не все эти данные обязательно используются в SQL.

### 1. Добавление одинарной кавычки

Передать символ ' и проверить, изменился ли ответ:
- появилась ошибка;
- изменилось содержимое страницы;
- возникло другое необычное поведение.

Кавычка может нарушить синтаксис SQL-запроса.

Однако ошибка сама по себе не доказывает SQL-инъекцию:
она могла возникнуть в другом коде приложения.

HTTP 500 означает внутреннюю ошибку сервера,
но не сообщает её причину.

### 2. Проверка вычисления SQL-выражений

Передать выражения, которые дают исходное значение
и другое значение, затем сравнить ответы.

Например, если числовой ввод попадает в SQL как выражение:
- 2 — исходное значение;
- 1+1 — выражение с тем же результатом;
- 1+2 — выражение с другим результатом.

Ожидаемое поведение может указывать на то, что ввод
вычисляется как SQL-код. Но нужно исключить другие
объяснения, например вычисление в самом приложении.

Синтаксис проверки зависит от контекста ввода.

### 3. Сравнение истинного и ложного условий

Передать два похожих ввода, отличающихся истинностью
добавленного условия.

В нашем учебном примере:

    Книги' AND 1=1-- 
    Книги' AND 1=2-- 

После двух дефисов стоит пробел.

Первый вариант возвращает обе книги:
условие 1=1 истинно, а фильтр публикации закомментирован.

Второй вариант не возвращает строк:
условие 1=2 ложно.

Повторяемое различие, соответствующее SQL-логике,
поддерживает гипотезу о SQL-инъекции.

Эти строки не универсальны: кавычки и комментарий
должны подходить к структуре исходного запроса.

### 4. Проверка через задержку ответа

Передать SQL-выражение, которое при выполнении
вызывает задержку.

Сравнить время ответа с обычными и контрольными запросами.
Один медленный ответ ничего не доказывает:
причиной могут быть сеть или нагрузка сервера.

Важна повторяемая задержка, связанная с нашим условием.
Конкретный синтаксис зависит от СУБД.

### 5. Проверка через внешнее взаимодействие — OAST

Передать выражение, которое при выполнении в базе
пытается вызвать обращение к контролируемому сервису,
например DNS-запрос.

Проверить, произошло ли ожидаемое обращение,
и связать его с конкретным тестовым запросом.

Метод зависит от возможностей СУБД, прав приложения
и сетевых ограничений.

### Автоматическая проверка

Burp Scanner может автоматизировать поиск SQL-инъекций.
Его результаты нужно проверять и понимать.

### Общий порядок

1. Сохранить обычный запрос и ответ для сравнения.
2. Менять один параметр за раз.
3. Сформулировать ожидаемый результат проверки.
4. Сравнить код ответа, содержимое и время ответа.
5. Повторить проверку и использовать контрольный запрос.
6. Отделить наблюдение от предположения о его причине.

Отсутствие ошибки или различий в одном тесте
не доказывает отсутствие SQL-инъекции.

## SQL-инъекция в разных частях запроса

SQL-инъекция возможна там, где приложение небезопасно
вставляет пользовательский ввод в SQL.

Примеры мест:
- SELECT: условие WHERE, имена таблиц и столбцов, ORDER BY;
- UPDATE: обновляемые значения после SET и условие WHERE;
- INSERT: добавляемые значения в VALUES.

### Контекст ввода

Строковый:

    SET email = '<ввод>'

Ввод окружён кавычками. Кавычка во вводе может изменить
границы строки.

Числовой:

    WHERE id = <ввод>

Ввод не окружён кавычками. SQL-выражение может изменить
условие без закрытия строки.

### Последствия зависят от команды

    WHERE id = 5 OR 1=1

Условие истинно для каждой строки:
- в SELECT — могут быть прочитаны все строки;
- в UPDATE — могут быть изменены все строки.

Замена одного значения другим сама по себе не является
SQL-инъекцией. SQL-инъекция изменяет структуру
или логику запроса.

## Примеры SQL-инъекций

Уязвимости SQL-инъекции встречаются в разных ситуациях, поэтому существуют разные способы их использования. Вот распространённые примеры:

- [Получение скрытых данных](https://portswigger.net/web-security/sql-injection#retrieving-hidden-data) — изменение SQL-запроса так, чтобы он вернул дополнительные результаты.
- [Нарушение логики приложения](https://portswigger.net/web-security/sql-injection#subverting-application-logic) — изменение запроса так, чтобы приложение работало не так, как задумано.
- [Атаки с `UNION`](https://portswigger.net/web-security/sql-injection/union-attacks) — получение данных из других таблиц базы данных.
- [Слепая SQL-инъекция](https://portswigger.net/web-security/sql-injection/blind) — ситуация, когда результаты изменённого вами запроса **не отображаются напрямую** в ответе приложения.

## Retrieving hidden data

Представьте интернет-магазин, в котором товары разделены на категории. Когда пользователь нажимает на категорию **Gifts** («Подарки»), браузер запрашивает адрес:

`https://insecure-website.com/products?category=Gifts`

После этого приложение выполняет SQL-запрос к базе данных:

`SELECT * FROM products WHERE category = 'Gifts' AND released = 1`

Запрос возвращает:

- все сведения о товарах (`*`);
- из таблицы `products`;
- у которых `category` равна `Gifts`;
- и `released` равен `1`.

Условие `released = 1` скрывает товары, которые ещё не выпущены. Можно предположить, что у таких товаров `released = 0`.

В приложении нет защиты от SQL-инъекций. Поэтому атакующий может, например, отправить запрос:

`https://insecure-website.com/products?category=Gifts'--`

В результате получится такой SQL-запрос:

`SELECT * FROM products WHERE category = 'Gifts'--' AND released = 1`

Здесь `--` обозначает начало комментария в SQL. Всё после него база данных игнорирует. Поэтому условие `AND released = 1` перестаёт действовать, и приложение показывает все товары категории **Gifts**, включая ещё не выпущенные.

Похожим способом можно заставить приложение показать товары **всех категорий**, даже тех, о существовании которых атакующий не знает:

`https://insecure-website.com/products?category=Gifts'+OR+1=1--`

Получится запрос:

`SELECT * FROM products WHERE category = 'Gifts' OR 1=1--' AND released = 1`

Он возвращает строки, для которых категория равна `Gifts` **или** условие `1=1` истинно. Поскольку `1=1` истинно всегда, запрос возвращает все товары.

#### Предупреждение

Будьте осторожны с условием `OR 1=1`. Приложение может использовать данные одного HTTP-запроса в нескольких SQL-запросах. Если это условие попадёт, например, в запрос `UPDATE` или `DELETE`, оно может привести к случайному изменению или удалению большого количества данных.

Из-за SQL-инъекции можно войти в логин без пароля.
При обычном входе пользователь вводит логин `wiener` и пароль `bluecheese`. Приложение подставляет их в запрос:

```
SELECT * FROM users
WHERE username = 'wiener' AND password = 'bluecheese'
```
Найди в таблице `users` пользователя, у которого логин — `wiener` **и одновременно** пароль – `bluecheese`. Если такая запись есть, приложение разрешает вход. Проблема возникает, если приложение **просто вставляет введённый текст в SQL-запрос**, не отделяя данные от команд. Тогда в поле логина можно передать:
```
administrator'--
```
После подстановки получается:
SELECT * FROM users
WHERE username = 'administrator'--' AND password = ''
Всё после `--` становится комментарием, включая проверку пароля. Поэтому фактически база выполняет только:
```
SELECT * FROM users
WHERE username = 'administrator'
```
Если аккаунт `administrator` существует, база возвращает его запись. А приложение в этом примере считает сам факт получения записи успешной проверкой логина и пароля – и разрешает вход, **хотя пароль вообще не проверялся**.

Название _Subverting application logic_ означает «обход логики приложения»: разработчик задумал проверку «логин **и** пароль», а пользовательский ввод изменил её на «только логин».

Защита от такого – **параметризованные запросы**, в которых введённый логин передаётся как значение, а не как часть SQL-кода. Тогда строка `administrator'--` будет восприниматься целиком как необычное имя пользователя и не сможет убрать проверку пароля.

SQL-инъекция с использованием UNION:
Исходный запрос получает названия и описания товаров категории `Gifts`:
```
SELECT name, description FROM products WHERE category = 'Gifts'
```
Если приложение просто подставляет введённый текст между кавычками, вместо `Gifts` можно передать следующую строку:
```
' UNION SELECT username, password FROM users--
```
Тогда итоговый запрос будет выглядеть так:
```
SELECT name, description FROM products WHERE category = ''
UNION SELECT username, password FROM users--'
```
Для такого примера оба `SELECT` должны возвращать одинаковое число столбцов, а типы соответствующих столбцов должны быть совместимы.

**Как UNION объединяет результаты запросов? и какие условия для этого нужны?**
Возьмём пример:
```
SELECT a, b FROM table1
UNION
SELECT c, d FROM table2
```
Первый запрос возвращает два столбца — `a` и `b`. Второй тоже возвращает два — `c` и `d`. `UNION` объединяет их строки в **одну таблицу результата с двумя столбцами**.

Для этого нужны два условия:

1. **Одинаковое количество столбцов.** Если первый запрос возвращает два столбца, второй тоже должен возвращать два. Объединить таким способом запрос с двумя столбцами и запрос с тремя не получится.
2. **Совместимые типы данных на соответствующих позициях.** Первый столбец первого запроса должен быть совместим с первым столбцом второго, второй — со вторым и так далее. Например, два текстовых столбца обычно совместимы. Для текста и числа результат зависит от правил преобразования типов конкретной СУБД.

Чтобы добавленный через инъекцию запрос сработал, нужно знать **число столбцов исходного результата** и **позиции, в которых можно вернуть нужный тип данных**, например текст.

**Как определить число столбцов в результате исходного запроса**, чтобы добавленный через `UNION` запрос возвращал столько же.?

Первый способ — `ORDER BY` с номером столбца.

Второй способ — `UNION SELECT` с разным количеством `NULL`.
